# 最長経路探索の速度改善

## 条件と注意

同じローカルデータ（1,985ノード・6,721辺）、各呼出し0.2秒、9シナリオ各5回。
表の時間は非プロファイル実行の中央値（グラフ構築は除き、planの前処理は含む）。
`before.json` / `iteration1.json` / `after.json` に全試行を保存した。
前回報告の「8/9件が打ち切り」は現環境では再現せず、変更前から8/9件が最適だった。
過去値でなく今回の変更前を基準に比較する。

## プロファイル

まず全体をcProfile計測。構築10.90秒の大半はbuild_bus / _sample_legsだったが、
構築はServiceで一度だけなので今回の変更対象外。
次に構築を除いて45回のplanを計測したところ、計4.093秒のうち
plan本体の自己時間2.307秒、sort 0.272秒、Dijkstra自己時間0.261秒、
append 0.252秒、next 0.231秒、区間キーのsorted 0.156秒。
DFSの反復と前処理が主要コストで、実装を確認すると同一区間・同時間の
複数路線を同一状態にもかかわらず別々に探索していた。
プロファイラ自体が時間制限下の解を変えるため、品質比較には計測器なしの値を用いた。

## 反復した改善

1. **同一区間・同所要時間の分岐を統合。** 使用済み区間・路線フィルター適用後に
   最初の辺だけを残す。資源、到着点、経過時間が一致するため探索状態は等価。
   所要時間の違う並行辺は、短い方にも締切上の価値があるので残す。
   池袋→品川は72,470→526分岐（99.3%減）、新宿一周は9,238→681。
   バスのみは239.5分の暫定解→240.0分の最適解、3,056分岐。
   9件の時間中央値の合計は0.5057→0.2604秒（48.5%減）。
2. **巨大整数の経路マスクをbytearrayに置換。** DFSは現在の経路だけを持つので、
   区間の使用状態をpush/popで更新すれば、状態ごとの巨大整数コピー・ビット演算が不要。
   分岐順・探索数は変更なし。中央値合計0.2604→0.2335秒（10.3%減）。
   短時間測定のばらつきを分離する補助実験として、8頂点完全グラフ、全辺1分、
   始点0・終点7、予算100分、clockが初めの1,000呼出しで0、その後100を返す
   固定作業量を7回測定。両実装とも112,000分岐・24分解で、中央値60.24→56.13ms
   （6.8%減）。実データでは既に全件最適なので、この段階で乗車時間の追加改善はない。

## チェック・再実行

```sh
cd transit_experiment
uv run python benchmarks/bench_longpath.py --seconds 0.2 --repeat 5 --json benchmarks/after.json
uv run python benchmarks/bench_longpath.py --seconds 0.2 --repeat 5 --profile search.prof
uv run python -m unittest discover -s tests
node tests/test_route.cjs
```

Python 49件とJSセルフチェック成功。追加テストは重複100本の探索数チェックと、
ランダム80多重グラフの総当たり比較（異なる並行辺重み、使用済み辺、路線フィルター、
始終点一致、締切、バックトラック時の使用権復元）。ベンチも各試行の経路を検証する。
`longpath-speed.patch` は変更前→変更後のソルバー差分。既存ソルバーが未追跡だったため、
変更前の再現用に保存した。比較用の別コピーで逆適用すれば変更前を復元できる。

## 残る課題

指数時間という性質は不変。今回の9件は全て予算上界に到達しただけで、
難しい任意の入力で高速に最適性を証明できるわけではない。
改善後は毎回の前処理・Dijkstraが主体。キャッシュにはネットワーク変更とフィルターの
無効化設計が必要なので今回は追加しない。前処理中に締切を調べない既存の性質も不変で、
極小のcompute_secondsでは上限を超えることがある。
同点解の代表路線は変わり得るが、乗車時間目的・使用権・道草・optimal/time_limitの契約は維持。
