# Tokyo Flow — メトロ・JR・都営バス Web マップ

既存の N02 GeoJSON を地図上に重ね、ODPT の運行情報を表示します。駅にマウスを重ねると駅名、路線をクリックすると強調表示します。スマートフォン対応。

## 最長経路実験（/route）

`uv run transit serve --host 127.0.0.1 --port 8000` で起動し、
<http://localhost:8000/route> を開きます。既存のマップ、N02駅データ、ODPTキャッシュ、
都営バスGTFS/SQLiteを再利用し、実験用の新規依存は追加していません。

### 操作

1. 出発・ゴール（候補入力または地図クリック）、**到着締切の日時**（端末のローカル時刻、24時間以内）を指定。
2. 電車路線・バス系統をチェックして「経路を探す」。乗車時間合計を最大化します。
3. 「出発」→「次の駅へ」で1区間ずつ進行。**出発後は手動シミュレーション時計**です。
   実際にボタンを押すまでの待ち時間は進まず、乗車所要分だけ進みます。画面に模擬日時を表示します。
4. ランチ等では経過分数を入力して「道草終了・再乗車」。時計・締切の残り時間だけ減り、
   乗車得点は増えません。使用済み区間は保持し、再計画は現在地から行います。
5. 乗り間違いは「予定外の乗車」で実際に乗った区間を順番に記録。
   選択フィルター外でも実績として記録でき、以後その区間は逆方向も使用不可です。
   「位置訂正」はテスト用の任意位置変更で、未申告の移動区間・時間は推測しません。
6. ゴール・フィルター変更後は再探索。締切は出発時に固定します。
   状態はページ内メモリのみ（再読み込み・リセットで消失）。GPSは不要です。

### モデルと判断

- **目的**は残り乗車分数の最大化。過去の乗車時間は固定得点なので再探索対象に含めません。
  **制約**は残り乗車時間が締切までの残り時間以下。乗換・渋滞・待ち時間は0です。
  実時刻表の接続、始終発、運休日は扱いません。実際の到着を保証する旅行案内ではありません。
- **区間**は無向の両端ノード対。路線違いでも同じ両端の区間は使用権を共有する保守的な定義です。
  同じ駅への再訪は可（単純パスではなくトレイル）。異なる停留所の区間が同じ道路上かどうかは未判定です。
- **所要時間**は0.1分単位。JRは既存12系統の駅順・45km/hモデル、メトロはODPT駅順＋直線距離÷35km/h。
  バスはGTFSの隣接停留所間所要時間の中央値、欠損は直線距離÷15km/h。
  運行時間帯・便の接続を考慮しない固定モデルにすることで、再計画と最長探索を独立して検証できます。
- **接続**は鉄道駅名一致、バスは「〈駅名〉駅…」の名称で鉄道と統合。
  同名かつ150m以内のバス乗り場を統合して対向停留所の逆走抜け道を抑制します。
  名前による統合は近似で、異名乗換駅や停留所の道路形状・一方通行は未対応です。
- **探索**は最短経路を実行可能初期解とし、ゴールへのDijkstra下界で枝刈りするDFS。
  明示スタックなので長い経路でも再帰上限に依存しません。NP-hardのため既定3秒で打ち切り、
  最良の有効候補を返します。`optimal` は全探索完了または予算上界到達（このモデル内のみ）、
  `time_limit` は最適性未保証。`LONGPATH_COMPUTE_SECONDS` は0超〜30秒。
- **データ**: JRのN02駅GeoJSONと `data/processed/bus-gtfs.sqlite` を使用。
  未取得時は下のインポート手順・起動時GTFS取得を使用し、取得完了後サーバーを再起動してください。
  グラフは初回アクセス時に構築しプロセス中は固定（履歴のエッジIDを安定させるため）。
  メトロはサーバー側の `ODPT_CONSUMER_KEY` で取得・24時間キャッシュし、取得失敗時は保存キャッシュを使用。
  キーなしでも保存済みキャッシュがあれば試せます。保存データは古い場合があり、運行可否を表しません。

### 反復検証・セルフチェック

既存の試作を実行してから以下を修正しました。

1. 路線違いの同一区間の再利用、小数誤差、タイムアウト時に候補なしになる問題を修正。
   小規模ランダムグラフ30例を独立した総当たりと照合し、1200区間の経路も検証。
2. 道草で予算が減らない、再計画が旧出発地を使う、駅再訪で進行が巻き戻る問題を修正。
   UIの状態遷移をNodeの標準 `assert` でチェック（ブラウザー描画テストではありません）。
3. バスの対向乗り場統合・欠損時間のフォールバック・メトロの欠損駅を飛ばして接続する問題を修正。
   ベンチマークの交通手段フィルター指定も修正して実データで再実行。
   手元の保存データでは1985ノード・6721辺。上限0.2秒の9シナリオ中8件が予算上界到達、
   バスのみ東京→両国は240分予算に対し239.5分の暫定解でした（環境・データで変化）。

```bash
cd transit_experiment
uv run python -m unittest discover -s tests -v
node tests/test_route.cjs
uv run python benchmarks/bench_longpath.py --seconds 0.2
```

探索APIは `POST /api/route/plan` に `start`, `goal`（ノードID）, `budget_minutes`,
`used`（区間IDの配列）, `allowed_routes`（路線ID配列、nullなら全路線、空配列なら全解除）を渡します。
グラフとIDは `GET /api/route/network`。不正なID・非有限値等は400です。
ローカル試験用サーバーであり、公開時の認証・負荷制御は別途必要です。

### 軽量表示

- 通常の路線・駅は Canvas で描画。路線の分割データを9路線の MultiLineString にまとめます。
- アニメーションは初期 OFF。路線選択後に「選択路線の動き ON」にすると、その1路線だけ SVG で描画します（最大1パス、15ステップ/秒）。
- アニメーションの発光フィルターは使いません。非表示タブや全路線表示ではアニメーションレイヤーを削除します。端末の視差効果を減らす設定にも従います。
- 外部 Web フォント・高解像度地図タイルを使わず、地図操作中のタイル更新も抑制します。

**動く線は視覚演出です。実際の列車位置・進行方向・本数は表していません。** 列車ピンは別途 `odpt:TrainTimetable` のダイヤから推定し、取得できる場合のみ `odpt:Train` の列車別遅延で補正します。運行情報は取得時点のもので、最新情報は事業者の公式案内も確認してください。

## 起動

Python 3.14 以降と uv を使用します。

```bash
cd transit_experiment
uv sync
cp .env.example .env
# .env の ODPT_CONSUMER_KEY にトークンを設定（コミットしない）

# data/processed の東京メトロ GeoJSON が未作成の場合のみ
uv run transit import-static-railways

uv run transit serve --host 0.0.0.0 --port 8000
```

ローカルでは http://localhost:8000 を開きます。Codespaces では Ports タブで 8000 を転送し、ブラウザーで開いてください（転送の公開範囲は Private を推奨）。キー未設定でも地図を表示でき、運行情報は「情報なし」となります。サーバーは起動時に `.env` を読み込むので、設定変更後は再起動してください。

既に GeoJSON があり、uv を使わずに表示だけ試す場合は、標準ライブラリのみでも起動できます（この方法では `.env` は自動読込されません）。

```bash
cd transit_experiment
read -rs -p 'ODPT key: ' ODPT_CONSUMER_KEY; echo
export ODPT_CONSUMER_KEY
PYTHONPATH=src python3 -c 'from transit_experiment.web import serve; serve("0.0.0.0", 8000)'
```

## 時刻表による列車位置の推定

**以前の各路線3個の参考配置は撤去しました。** 実際の列車番号・各駅の発着時刻に基づいて推定します。「平常運転だから誤差ゼロ」とは扱いません。

1. `odpt:TrainTimetable` を路線・運行日種別ごとに取得。平日／土休日を使い分けます。APIが上限の1000件を返した場合は、不完全な時刻表を採用せず取得失敗として扱います。
2. 日本時間の現在時刻を列車ダイヤと比較して、どの駅間にいるかと経過割合を計算。例：12:00発→12:04着なら、12:02に区間の50%と推定します。到着・出発の両方があれば停車時間も反映します。出発時刻しかない場合は、停車時間込みの区間平均速度になります。
3. N02の路線グラフから駅間の経路を求め、経路の距離に沿って補間します。線路接続が見つからない場合だけ両駅の直線補間にフォールバックし、ポップアップに明記します。2022年の形状、駅座標のスナップ、等速仮定による誤差があります。
4. `odpt:Train` に新鮮な列車別 `odpt:delay`（秒）があれば、その列車のダイヤを遅延分ずらします。APIが0件でも時刻表の推定は可能です。
5. 運行のお知らせがある路線や遅延秒数が正の列車は赤表示。路線単位の文章から遅延分数を推測して全列車に適用することはしません。遅延量不明なら赤表示のみです。運行情報が古い・不明な場合は灰色枠で区別します。

メトロの列車ポップアップには、実時刻表に記載された該当区間の発着予定時刻も表示します（深夜は「翌」と表記）。

画面は30秒ごとに `/api/estimates` を参照し、サーバーの計算結果も15秒共有します。ピンは Canvas の矢印で表示し、線路経路の接線から進行方向を求めます。停車中は次区間への発車方向、終着では到着方向を示します。方向不明時だけひし形にします。常時アニメーションや列車ごとのDOM追加は行いません（Leaflet 1.9.4 の Canvas 描画フックを使用）。列車番号・駅間・計算時刻・時刻表更新日・補正内容をクリックで確認できます。計算から180秒以上古いピンは隠します。運休・臨時ダイヤ・加減速など、APIで判断できない変更は反映できません。

### 日付・祝日

- JST 03:00を運行日の境界として、深夜0～2時台は前日のダイヤで計算。24時超の時刻表記にも対応します。
- `src/transit_experiment/holidays.csv` は[内閣府の国民の祝日CSV](https://www8.cao.go.jp/chosei/shukujitsu/syukujitsu.csv)を2026-09-29に取得したものです（2027年まで）。対応年を超えたら推定を停止するため、毎年更新してください。
- 土日・祝日と12/30～1/3を土休日扱いにしています。特別ダイヤ・臨時ダイヤの自動判定には対応していません。

### 時刻表キャッシュ

- 時刻表・駅マスターは24時間、運行情報・列車別遅延データは120秒キャッシュ。キーはサーバーだけで保持します。
- 時刻表は起動後バックグラウンドで当日の9路線＋丸ノ内支線を直列取得し、各路線の処理間に2秒空けます。通常の初回は10回、更新は1日1回／路線・曜日種別です。取得中は画面に取得待ちの路線数を表示します。
- ODPTリクエスト全体も単一プロセス内で直列化し、開始間隔を最低2秒にします。
- 再起動時はディスクキャッシュと再試行可能時刻を引き継ぎます。更新失敗時の時刻表は警告付きで最大7日まで利用し、それを超えたら非表示にします。
- `/api/trains` は駅・区間の実データ確認用として残していますが、現在の画面は `/api/estimates` を使います。

## JR・都営バスの表示

画面上部の「表示する交通機関」で **東京メトロ / JR東日本 / 都営バス / すべて** を切り替えます。「すべて」では3交通機関の路線・駅・推定矢印を同じ地図に重ねます（バス停ピンは未対応）。それ以外では選択した交通機関だけを Canvas で表示します。

「すべて」でもJR・バスは画面範囲内のみ取得し、**JR＋バス合計600個**に矢印を制限します。上限時は両方が残るよう交互に採用し、画面に制限を明記します（メトロの矢印は別枠）。路線IDは事業者別に区別し、片方の取得失敗でも取得できた交通機関とメトロを残します。「全体を表示」は3交通機関の範囲に対応します。メトロとJR・バスの路線絞り込み・矢印ON/OFFは独立しています。路線・系統の絞り込み、矢印表示ON/OFF、進行方向、便ごとのポップアップに対応します。

### JR東日本

- 時刻表未取得でも既存の `jr-east-railroads.geojson` による路線図と `jr-east-stations.geojson` による駅ピンを表示します。小さい丸が駅、矢印が推定列車です。駅名はホバー・クリックで確認でき、路線の絞り込みにも連動します。駅座標はN02の駅区間の中点で、現行の駅・出口の正確な場所とは異なる場合があります。通常は下記の12系統の簡易モデルを表示し、モデル作成に必要なデータがないときだけN02の線路名称による静的地図に戻ります。
- **実時刻表なしの簡易推定**：山手線・中央線・中央総武線・京浜東北線・埼京線・常磐線・京葉線・南武線・横浜線・武蔵野線・青梅線・五日市線の12系統を収録範囲内で表示します。駅順は手動定義で、快速・各停の種別、直通・支線、臨時運行は完全には再現しません。
- 仮定は5〜15分間隔（系統別）、走行45km/h・駅停車30秒、05:00〜翌01:00。同じモデルを平日・休日に使います。**これらは公表ダイヤではなく表示用の仮定**です。遅延は無視し、実際の列車位置・本数・始終発を保証しません。画面・矢印のポップアップ・APIに `headway_model` /「簡易推定」を明記します。
- N02の線路形状に沿い、双方向の位置を時計から決定します。ランダム配置ではありません。山手線は環状の駅順です。線路の接続不備による極端な迂回は直線近似として扱い、駅データが足りない系統は表示しません。
- この簡易モデルは追加のキーもAPI取得も不要です。経路を起動時に共有し、位置計算は数ミリ秒程度・30秒ごとに画面更新します。仮定値・対象駅順は `src/transit_experiment/jr_model.py` にあります。
- JRの実時刻表は[ODPTカタログ](https://ckan.odpt.org/dataset/jreast_tokyo_area)で指定された **チャレンジ2026用GTFS** を使用します。通常のキーでは403でした。
- 利用資格・規約を確認して取得したチャレンジ用トークンを `.env` の `ODPT_CHALLENGE_KEY` に設定し、サーバーを再起動するとインポートを試みます。GTFSが利用できる場合は簡易モデルより優先します。
- GTFSが使える場合、提供対象の路線だけを時刻表・形状に基づいて表示します。遅延・運休情報は未連携です。**実際のJR GTFSによる推定は403のため未検証**です。共通インポーターはテスト用GTFSで検証しています。
- キー以外に、利用権限のあるJR GTFS ZIPをローカルから取り込む方法にも対応します。`uv run transit import-jr-gtfs /path/to/feed.zip` のあとにサーバーを再起動してください。保存済みの実時刻表DBが簡易モデルより優先されます。
- [公式時刻表の調査結果](../docs/transport-data/timetable-research.md)も参照してください。JR公式Web時刻表には無断転載・加工を禁じる注意書きがあり、無許諾の一括取り込みはしていません。
- チャレンジ限定データの利用期間・配信可否等を確認してください。通常の公開地図の権限とは別です。

### 都営バス

- 東京都交通局の[公開GTFS](https://api-public.odpt.org/api/v4/files/Toei/data/ToeiBus-GTFS.zip)を使用。追加トークンは不要です。2026-09-29の確認時点で150系統・748経路です。
- `calendar.txt` と `calendar_dates.txt` による運行日・例外日、24時超の便、`feed_info.txt` の有効期間を反映します。GTFSの便ごとの発着時刻と `shapes.txt` の道路形状に沿って位置・方向を補間します。
- 停留所の並びを経路に単調に対応づけ、同じ地点を通る経路で安易に逆方向へ補間しないようにしています。形状がない／十分近くに対応づけられない場合は停留所間の直線近似と明記します。信号待ち・加減速は推定できません。
- **バスの遅延・運休・渋滞・GTFS-Realtimeは未連携**です。通常色でも定刻運行とは限りません。全社の路線バスではなく、まず都営バスのみを対象にしています。
- GTFSの欠落した停車時刻や `frequencies.txt` の頻度運行は現在補完しません。GTFS日付は当日・前日の便を確認します（48時以上の運行は未対応）。

### GTFSの軽量化・キャッシュ

- バスは起動時から、JRはチャレンジキー設定時に、GTFSをバックグラウンドで準備します。ZIPの取得は24時間に1回、再起動後も再利用します。取得・コンパイル失敗時は保存済みDBを保持し、キャッシュのバックオフに従って再試行します。
- GTFSはZIPからストリーミングで読み、約100万行の停車時刻を辞書配列で常駐させずSQLiteへ格納します。データは `data/raw/{bus,jr}-gtfs.zip` と `data/processed/{bus,jr}-gtfs.sqlite`（gitignore対象）です。
- 位置計算は20秒間共有、ブラウザーは30秒更新。画面範囲・路線で絞り込んで返し、最大600個の矢印だけ描画します。上限時は画面に明記します。非表示タブ・メトロ表示中は追加交通機関のポーリングを停止します。
- 大きなレスポンスはgzip圧縮。系統ごとに線形をまとめ、路線切り替え後の不要なレイヤーは削除します。
- GTFSファイルの更新は起動中に継続します。通常JSON APIと別ホストのGTFS取得は独立したキャッシュです。

## キャッシュとレート制限

- キーはサーバー側の環境変数にのみ保持。ブラウザーに送らず、API URL・例外にも出力しません。
- 運行情報は全閲覧者で共有する **120秒 TTL**。9路線＋丸ノ内支線の運行情報を1回で取得します。ブラウザーは自サーバーを120秒ごとに確認し、非表示タブではポーリングを休止します。
- キャッシュ期限切れ時のリクエストだけが ODPT を呼びます。同時リクエストはロックで集約し、重複取得を防止します。運行情報・列車データは閲覧者がいない間は取得しません。時刻表のバックグラウンド更新は起動中継続します。
- 正常取得から120秒以内は再取得しません。エラー時は240秒から最大1800秒までバックオフし、429等の `Retry-After`（秒数・HTTP日付）も尊重します。401/403時は最低1800秒待機します。
- 失敗時は最後の成功データと取得日時を保持し、「保存情報」と警告を表示します。未取得を「平常運転」として扱いません。
- データ・次回取得可能時刻を `data/processed/realtime/web-status-cache.json` に保存し、サーバー再起動後も利用します。キーは保存しません。このディレクトリは gitignore 対象です。
- この制御は **単一サーバープロセス** のためのものです。複数プロセス・複数インスタンスへ拡張する場合は Redis 等の共有キャッシュと分散ロックが必要です。別の CLI/API クライアントによる呼び出しとは共有しません。

## データ・配信

- 路線と駅：国土数値情報 N02（2022年）。既存の分割された線形をそのまま描画するため、接続や位置には元データ由来の誤差があり、光の移動は線分ごとです。現行路線との相違に注意してください。
- 運行情報・時刻表・列車別遅延・駅座標：公共交通オープンデータセンター（ODPT）／東京メトロ。
- 地図：CARTO / OpenStreetMap。Leaflet は CDN から取得するためインターネット接続が必要です。
- 公開前に各データ提供元・地図タイルの利用条件と必要なクレジットを確認してください。
- Python 標準ライブラリの HTTP サーバーを使った開発用ビューアーです。本番公開には TLS・アクセス制御・リバースプロキシ等を追加してください。
