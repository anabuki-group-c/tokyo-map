# Design Model

**設計では、コードの編集箇所ではなく、どんな仕組みを成立させるかを考える。**
実現したい振る舞い、各部分の役割と関係、守る条件を決め、その具体化として関数・引数・ファイルの変更を考える。
考えている途中やplanを書くときに、今扱っている粒度を確かめるためのガイド。

## The scale — 考える粒度

| 粒度 | 例 | 何が決まっているか |
|---|---|---|
| 粗すぎる | 「データ取得を安全にする」 | 目的だけ。何をどう成立させるかは分からない。 |
| 設計で考えたい粒度 | 「複数の取得要求が重なったら、要求と結果を対応付け、最後に要求した結果だけを表示へ反映する」 | 振る舞い、必要な関係、古い結果で表示を上書きしないという条件。 |
| 実装へ下りた粒度 | 「要求番号のフィールドを追加し、応答時に比較するifを入れる」 | 特定のデータ構造とコードによる実現方法。 |

これは「最後の要求を優先する」という仕様を選んだ場合の例。実際に必要な仕組みは、対象の要件・コード・仕様から確かめる。
実装の粒度も必要だが、それだけを書いて設計を済ませない。逆に、目的や原則を述べただけでも設計は決まらない。

## Questions — 粒度を確かめる問い

- **関数名やファイル名を外しても、仕組みを説明できるか？** 名前の代わりに、何が何を受け取り、どう判断し、何を変えるかを捉える。
- **目的だけでなく、成立させる方法が決まっているか？** 役割、情報の流れ、状態の変化、失敗時の扱いを、対象に必要な範囲で説明できるか。
- **何を守れば正しく、何が起きると誤りか分かるか？** 検証できる条件まで具体化する。「安全に」「適切に」で止めない。
- **今の細部は設計を左右するか、後から選べる実装方法か？** その細部を替えたとき、振る舞いや保証が変わるかで判断する。

すべての項目を埋める手順ではない。考えがコード編集へ寄りすぎたとき、または抽象的すぎて何も決まっていないときに、必要な問いで調整する。

## Decisions — どこまで決めるか

**設計で決めるもの：** 実現する振る舞い、役割の分担、情報や状態の関係、成立条件、失敗時の扱い、その構造を選ぶ理由。

**実装で選べるもの：** それらを保ったまま変更できる、内部の命名、関数分割、データの格納方法など。

この区別は、コードの要素名ではなく、影響で決める。
外部に公開する引数、データ形式、丸め規則、処理順、資源の寿命などが正しさや互換性を左右するなら、その具体性は設計に残す。

既存のクラスやフラグを、そのまま設計上の役割とみなさない。必要な役割と関係を捉えてから、現在のコードでどう実現されているかを対応付ける。
実装上の制約で仕組みが成立しないと分かったら、設計へ戻って見直す。

## Plan — 計画に落とす

planには、仕組みとして決めたことと、それを実現するコード変更を区別して書く。
読み手が、編集手順を追わなくても「どういう設計にするか」を理解できるようにする。

上の例なら、次のように書き分けられる。

- **設計：** 要求と結果を対応付け、最後の要求に一致する結果だけを表示へ反映する。古い要求が後から完了しても、新しい結果を上書きしない。
- **実装への対応：** 現在の要求を識別する値を保持し、結果を受け取る場所で照合する。ここで必要な関数・引数・変更ファイルを具体化する。
- **検証：** 2つの要求が発行順と逆に完了しても、最後に要求した結果が表示されることを確かめる。

これは粒度を分ける例であり、固定テンプレートではない。設計が既に決まっているなら、その前提を短く示して実装計画へ進んでよい。

## Rules

- **仕組みまで具体化する。** 目標だけでも、コードの操作一覧だけでも終えない。何がどう関係して必要な動作を成立させるかを決める。
- **抽象化は曖昧化ではない。** 正しさを左右する数値・条件・順序は残す。説明を大づかみにするために必要な精度を落とさない。
- **要件と実コードを根拠にする。** 現在の挙動、満たすべき仕様、今回の提案、未確認の点を区別する。先に考えたモデルへ現実を無理に合わせない。
- **設計の成立を確かめる。** 想定した実装に合わせるだけでなく、要件や確認済みの条件から検証を考える。

## Boundaries

このskillは、設計時に何をどの粒度で決めるかを扱う。設計書の管理方法や、委任・報告の形式は規定しない。
細かな実装計画は、設計を具体化するために必要な範囲で書く。小さな変更のたびに新しい設計書を作る必要はない。
仕組みを整理することは、コードへ抽象クラスや汎用基盤を追加することではない。

**仕組みとして決める。その後で、コードへ具体化する。**
