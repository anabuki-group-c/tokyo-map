# Long Route Times — 東京の周辺施設検索API

卒業研究「Long Route Times」の一部として、現在地から半径 **Xメートル以内** にある飲食店や観光地を検索するAPIを開発するプロジェクトです。東京の地理データには [Overture Maps](https://overturemaps.org/) を利用します。

> このREADMEは、卒業研究スライドと今回の開発方針に基づく計画書です。周辺施設検索APIと動作確認用の簡易UIはPythonで実装済みです（[実行方法](#実行方法)）。実データでの分類対応表の確認と性能評価は未実施です。

## 卒業研究の概要

**Long Route Times：身近な東京の新しい一面を見つける、移動時間の最大化アプリ**

最短・最速の移動に加えて、遠回りや乗り換えの待ち時間を、街を探索する機会として活用するアプリを目指します。出発地・目的地・到着希望時刻をもとに、東京都内の公共交通を使った経路や、移動の途中で訪れられる場所を提案する構想です。

スライドでは、経路の逆走や途中下車を制限し、到着希望時刻を守る条件のもとで、移動や待ち時間を最大化する経路探索を検討しています。研究全体では、制約の充足、探索の計算時間、利用者が得た発見や楽しさを評価する予定です。

## 今回の開発目的

Google Mapsなどで利用できる周辺スポット検索に相当する機能を、Overture Mapsのデータを使った独自APIとして作成します。

利用者の現在地と検索半径を受け取り、範囲内の飲食店・観光地の情報を返します。フロントエンドはこの結果を利用して、地図上のマーカーや一覧を表示します。将来的には、研究アプリの寄り道先候補の取得に利用します。

### 初期開発の範囲

- 対象地域：東京都全体（島しょ部を含む）。Overture Mapsの行政区域（Divisions）にある東京都の境界ポリゴンで判定し、他県の施設は除外する。
- 検索の中心：端末などから取得した現在地の緯度・経度。
- 検索距離：指定地点から半径Xメートル以内の直線距離。
- 検索対象：飲食店、観光地。
- 出力：施設ID、名称、分類、緯度・経度、現在地からの距離など。
- 簡易UI：APIの動作確認用に、検索条件の入力と結果の地図・一覧表示ができる簡単な画面を作成する。

半径による検索は、徒歩の所要時間や道路に沿った移動距離とは異なります。公共交通の経路探索や到着時刻に基づく寄り道の判定は、今後の拡張として扱います。

## データについて

現在、Overture Mapsから東京の地図データを取得する取り組みを進めています。施設検索には、店舗やランドマークなどの地点情報を含む **Places** テーマの利用を想定しています。道路・建物などのデータだけを取得している場合は、Placesの追加取得が必要です。

参考資料：

- [Overture Maps公式サイト](https://overturemaps.org/)
- [Placesガイド](https://docs.overturemaps.org/guides/places/)
- [データ取得ガイド](https://docs.overturemaps.org/getting-data/)
- [データの帰属表示・ライセンス](https://docs.overturemaps.org/attribution/)

### 取得済みデータの確認事項

- リリース名・取得日・対象地域の抽出条件を記録する。
- Placesの施設情報、名称、座標、分類が含まれているか確認する。
- 分類のプロパティ名と値を確認し、APIの「飲食店」「観光地」への対応表を作る。
- 欠損値、重複、閉業などによるデータの不一致を確認する。
- 利用するテーマとデータのライセンス・帰属表示条件を確認する。

公式Placesガイドでは、2026年9月リリースから従来の `categories` を削除し、`taxonomy` と `basic_category` に移行したと説明しています。取得済みデータが旧リリースの場合もあるため、実際のスキーマに合わせて処理します。

観光地は本API側で定義する検索区分です。博物館、名所など、どの分類を対象に含めるかを決めます。公園などを含める場合は、Placesでの収録状況を確認し、必要に応じて別テーマの利用を検討します。

## 想定する処理の流れ

1. クライアントが利用者の位置情報への許可を得て、現在地を取得する。
2. クライアントが緯度・経度、検索半径、施設区分をAPIに送信する。
3. APIが入力値を検証し、東京の施設データから候補を抽出する。
4. 候補までの距離を計算し、半径以内の施設を距離順で返す。
5. クライアントが検索結果を地図や一覧に表示する。

API自体が端末の現在地を取得するわけではなく、クライアントが送信した座標を検索の中心に使います。

## API仕様案

### 周辺施設の検索

```http
GET /api/v1/places/nearby
```

| パラメータ | 必須 | 内容 |
| --- | --- | --- |
| `lat` | 必須 | 緯度。-90〜90の数値 |
| `lon` | 必須 | 経度。-180〜180の数値 |
| `radius_m` | 必須 | 検索半径（メートル）。0より大きい数値 |
| `category` | 任意 | `restaurant`（飲食店）、`tourism`（観光地）、`all`（両方）。省略時は `all` |
| `limit` | 任意 | 返却件数の上限。省略時は20件、指定可能範囲は1〜100件 |

検索半径の上限は暫定で5000メートルとしています。対象データの件数と応答時間を測定して見直します。

#### リクエスト例

```http
GET /api/v1/places/nearby?lat=35.681236&lon=139.767125&radius_m=500&category=restaurant&limit=20
```

#### レスポンス例

以下は形式を示す架空のデータです。

```json
{
  "center": { "lat": 35.681236, "lon": 139.767125 },
  "radius_m": 500,
  "category": "restaurant",
  "count": 1,
  "partial_coverage": false,
  "places": [
    {
      "id": "example-place-id",
      "name": "サンプル飲食店",
      "category": "restaurant",
      "source_category": "casual_eatery",
      "lat": 35.682,
      "lon": 139.768,
      "distance_m": 116.3,
      "address": null
    }
  ]
}
```

- `category` はAPIで定義する区分であり、Overtureの元の分類名は `source_category` として分けて返す。
- `count` は今回返した件数。検索範囲内の全件数を意味しない。
- 名称や住所の欠損は `null` とする。
- 半径の判定には丸める前の距離を使い、`distance_m` は表示用に丸める。
- 該当する施設がない場合は、HTTP 200で `count: 0` と `places: []` を返す。
- 東京都の範囲外を中心に指定した場合は、HTTP 400でエラーコード `OUT_OF_COVERAGE` を返す。
- 検索円が東京都の外（他県や海）にかかる場合は `partial_coverage: true` を返す。都外の施設は結果に含まれない。判定は円周上の32点が都内にあるかで行う近似。
- 施設データが未取込の場合は、HTTP 503でエラーコード `DATA_NOT_READY` を返す。

#### エラー例

不正な座標、0以下の半径、未対応の検索区分などはHTTP 400で返します。

```json
{
  "error": {
    "code": "INVALID_PARAMETER",
    "message": "radius_mには0より大きい数値を指定してください。"
  }
}
```

## 検索処理の設計方針

施設の座標を検索できる形で保存し、空間インデックスや検索範囲を囲む矩形によって候補を絞り込みます。その後、メートル単位の距離判定で、中心からの距離が `radius_m` 以下の施設を抽出します。

緯度・経度の差をそのままメートルとして扱わず、地理座標に対応した距離計算を利用します。保存形式によっては座標が経度・緯度の順になるため、API入力との取り違えに注意します。

実装は `transit_experiment` と同じく、Python標準ライブラリだけで構成しています。

- データ保存：SQLiteに施設を保存し、R*Tree（空間インデックス）で検索範囲を囲む矩形の候補を絞り込む。
- 距離計算：候補ごとにhaversine式で距離（メートル）を計算し、`radius_m` 以下の施設を距離順に返す。
- APIサーバ：`http.server` を使う。位置情報を含むクエリ文字列はログに残さない。
- 取込時の除外：座標のない施設、閉業（`operating_status` が `closed` など）の施設、飲食店・観光地に該当しない施設、東京都の境界の外にある施設、重複IDは取り込まない。
- 東京都の判定：Overtureの `division_area` のうち、`region` が `JP-13`、`subtype` が `region`、`class` が `land`（陸地）の境界ポリゴンを使う。住所の文字列ではなく座標で判定する（Overtureの住所には、座標と食い違うものがあるため）。境界は緯度の帯ごとに辺を分けて保持し、点が境界の内側かを高速に判定する。

### 分類対応表

`src/nearby_places_api/categories.py` で、Overtureの分類をAPIの区分に対応付けています。現行の `taxonomy`・`basic_category` と、旧リリースの `categories` の両方を参照します。2026年10月5日に取得した都心部（東経139.69〜139.81度、北緯35.65〜35.73度）のPlaces 168,702件を使い、観光地の対応表を見直しました。

**飲食店（`restaurant`）**：最上位分類が `food_and_drink`（旧 `eat_and_drink`）、または `restaurant`・`eatery`・`cafe` などで終わる分類。都心部では64,176件。

**観光地（`tourism`）**：都心部では3,420件。

| 対象 | Overtureの分類 | 都心部の件数 | 例 |
| --- | --- | ---: | --- |
| 寺院 | `buddhist_place_of_worship` | 約840 | 浅草寺、増上寺 |
| 神社 | 宗教系の分類で、名前が「神社・神宮・天満宮・天神・稲荷・寺」などで終わるもの | 約270 | 明治神宮、根津神社、日枝神社 |
| 公園・庭園 | `park`、`national_park`、`garden`、`botanical_garden` | 約800 | 上野恩賜公園、駒込の六義園 |
| 史跡 | `historic_site`（名前で絞り込み）、`palace` | 約590 | 皇居、金座跡、猫又坂 |
| 博物館・美術館 | `museum` とその下位分類すべて | 403 | 東京国立博物館、国立西洋美術館 |
| 記念碑 | `monument` | 244 | 記念碑、歌碑 |
| 動物園・水族館・遊園地 | `zoo`、`aquarium`、`amusement_park` | 約100 | 恩賜上野動物園 |
| 展望台・プラネタリウム | `observatory`、`planetarium` | 14 | 東京タワー |
| 自然 | `mountain`、`beach`、`nature_reserve`、`lake` | 約70 | 高尾山山頂 |
| パブリックアート | `sculpture_statue`、`street_art` | 55 | 湯島天神の撫で牛 |
| 観光案内所 | `visitor_center` | 17 | |
| 分類のない展望施設 | 分類が空で、名前に「展望室・展望台」を含むもの | | 東京都庁舎展望室 |

データを確認して分かったことと、その対応は次のとおりです。

- **神社に専用の分類がない**：明治神宮・靖国神社はキリスト教の礼拝所（`christian_place_of_worship`）、湯島天神は宗教団体（`religious_organization`）、日枝神社は分類なしになっている。そのため神社は、宗教系の分類または分類なしの施設のうち、名前の語尾で判定する。教会や宗教団体の事務所は語尾が合わないため含まれない。
- **`historic_site` にマンションやビルが混ざる**：「〜レジデンス」「〜タワー」「〜ビル」などが約900件ある。名前に「跡・碑・墓・坂・門・旧・記念・資料館・邸・城・橋・庭園」などを含み、「レジデンス・マンション・タワー・ビル・歩道橋」などを含まないものだけを観光地にする。
- **含めないもの**：児童遊園・児童公園・ドッグラン（小規模で寄り道先に向かないため）、ギャラリー（`art_gallery`、約1,300件。多くは商業ギャラリーのため）、劇場・ライブハウス・スタジアム、橋・桟橋、墓地、旅行会社。
- **限界**：名前による判定のため、漏れや誤判定は残る。分類自体の誤りもある（新宿御苑のレコードの1つが和食店に分類されているなど）。対応表を変えた場合は、`places import` で取り込み直す。

旧スキーマの分類（`tourist_attraction`、`landmark_and_historical_building`、`shinto_shrine` など）も、互換のため引き続き観光地として扱います。

## 簡易UI

APIの動作を目で確認するため、ブラウザで使える簡単な画面を作成します。研究アプリ本体のUIではなく、開発・検証用の位置づけです。

- 現在地の取得ボタン、または地図のクリックで検索の中心を指定する。
- 検索半径（`radius_m`）、施設区分（`category`）、件数上限（`limit`）を入力できる。
- 検索の中心と半径の円、該当施設のマーカーを地図上に表示する。
- 施設の名称、分類、距離を距離順の一覧で表示する。
- 該当なしやエラーの場合は、その旨を画面に表示する。

`transit_experiment` と同じく、地図には Leaflet 1.9.4（CDNから読込）を使い、APIサーバが画面のHTML・JavaScript・CSSも配信します。背景地図は国土地理院の地理院タイル（淡色地図）です。CARTOのタイルはAPIキーが必要になっていたため使っていません。

- 東京都の境界を点線で表示する（`GET /api/v1/places/coverage` で取得）。島しょ部まで含めると表示範囲が広すぎるため、初期表示は都心にする。
- マーカーの色は、飲食店がオレンジ、観光地が青。一覧の項目を押すと、地図上でその施設の詳細を表示する。
- 施設名などはテキストとして表示し、HTMLとしては解釈しない。

## 実行方法

Python 3.14以上と [uv](https://docs.astral.sh/uv/) を使います。外部ライブラリには依存していません。

### 1. データの取得

Overture公式の `overturemaps` CLI（`pip install overturemaps`）で、東京都の境界と施設データをGeoJSONSeq形式で取得し、`data/raw/` に置きます（`data/raw` と `data/processed` はコミットしません）。

**東京都の境界**：`division_area` は、指定した範囲に重なる行政区域をポリゴン全体で返します。東京駅付近の小さな範囲を指定すれば、島しょ部を含む東京都全体の境界が取得できます。

```bash
overturemaps download --bbox=139.76,35.68,139.77,35.69 -f geojsonseq --type=division_area -o data/raw/tokyo-division-area.geojsonseq
```

**施設（Places）**：東京都は本土と島しょ部が離れているため、範囲を分けて取得します。範囲に含まれる他県の施設は、取込時に境界で除外されます。

```bash
# 本土（23区・多摩地域）
overturemaps download --bbox=138.94,35.49,139.93,35.90 -f geojsonseq --type=place -o data/raw/tokyo-places-mainland.geojsonseq
# 伊豆諸島
overturemaps download --bbox=139.10,32.40,140.40,34.80 -f geojsonseq --type=place -o data/raw/tokyo-places-izu.geojsonseq
# 小笠原諸島
overturemaps download --bbox=141.20,24.20,142.30,27.80 -f geojsonseq --type=place -o data/raw/tokyo-places-ogasawara.geojsonseq
```

取得したリリース名と取得日を記録してください。`overturemaps releases list` でリリースの一覧を確認でき、`-r 2026-09-23.1` のように指定すると同じリリースを取得し直せます。

現在の取得済みデータは次のとおりです。

| 項目 | 内容 |
| --- | --- |
| リリース | `2026-09-23.1` |
| 取得日 | 2026年10月5日 |
| 読み込んだ施設 | 588,983件（本土 587,318件、伊豆諸島 1,336件、小笠原 329件） |
| 取り込んだ施設 | 飲食店 146,567件、観光地 11,898件 |
| 除外した施設 | 対象外の分類・閉業など 390,008件、東京都外 40,510件 |GeoJSON（FeatureCollection）形式も取り込めますが、ファイル全体をメモリに読み込むため、大きなデータにはGeoJSONSeqを使います。

### 2. 取込

```bash
cd nearby_places_api
uv run places import data/raw/tokyo-places-*.geojsonseq --boundary data/raw/tokyo-division-area.geojsonseq
```

`data/processed/places.sqlite` が作成されます。複数のファイルをまとめて取り込めます。境界ファイルから東京都の陸地のポリゴンを取り出し、その内側の施設だけを保存します。取込結果として、都外として除外した件数（`outside Tokyo`）も表示されます。

### 3. APIの起動

```bash
uv run places serve --host 127.0.0.1 --port 8000
curl "http://127.0.0.1:8000/api/v1/places/nearby?lat=35.681236&lon=139.767125&radius_m=500&category=restaurant&limit=20"
```

### 4. 簡易UIを開く

サーバを起動した状態で、ブラウザで http://127.0.0.1:8000/ を開きます。地図をクリックするか「現在地を取得」を押すと、その地点を中心に検索します。現在地の取得には、ブラウザでの位置情報の許可が必要です（`localhost`・`127.0.0.1` 以外の http では取得できません）。地図ライブラリと地図タイルの読込にはインターネット接続が必要です。

VS Code の Live Server などで `static/index.html` を直接開いた場合は、`http://127.0.0.1:8000` で起動したAPIに接続します。この場合も `uv run places serve` でAPIを起動しておいてください（APIは `localhost`・`127.0.0.1` からのページにだけ応答を許可しています）。

### 補助API：東京都の境界の取得

```http
GET /api/v1/places/coverage
```

取込時に使った東京都の境界を `{"bbox": [最小経度, 最小緯度, 最大経度, 最大緯度], "boundary": GeoJSONのジオメトリ}` で返します。データ未取込の場合はHTTP 503（`DATA_NOT_READY`）です。

## テスト

```bash
cd nearby_places_api
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

テストでは架空の施設データを使い、半径の内側・境界・外側の判定、東西方向の距離計算、分類の対応、閉業や重複の除外、距離順、件数上限、該当なし、不正入力、都外の地点、都の境界をまたぐ検索、境界ポリゴンの判定（穴・離島を含む）、行政区域データからの東京都の抽出を確認しています。
